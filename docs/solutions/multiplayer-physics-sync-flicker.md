## 요약

대전 참가자 화면에서 물체가 약 2.5초마다 짧게 깜빡이거나 다른 자리로 순간이동해 보였다.

방장과 참가자가 각자 Rapier 물리를 실행하므로 두 물리 세계는 프레임 간격과 메시지 도착 시점의 차이만으로도 조금씩 벌어진다. 방장은 2.5초마다 권위 키프레임을 보내 이 차이를 되돌리는데, 기존 참가자는 키프레임을 받은 프레임에 물체를 방장 좌표로 즉시 옮기고 속도까지 0으로 만들었다. 물리 상태를 맞추는 동작 자체는 필요했지만, 그 불연속을 그대로 렌더링한 것이 깜빡임의 직접 원인이었다.

해결은 **판정에 쓰는 물리 상태와 참가자가 보는 표시 상태를 분리하는 것**이었다. 참가자 물리는 키프레임 수신 즉시 방장 상태로 복원하되, 화면만 직전 위치에서 새 위치까지 120ms 동안 이어 붙였다. 동시에 생성 높이, 속도, 휴면·정착·앵커 등 다음 물리 스텝에 영향을 주는 상태도 방장 값으로 복원해 교정 직후 다시 벌어지는 원인을 줄였다.

## 증상

- 참가자 화면의 물체가 일정한 간격으로 짧게 순간이동했다.
- 낙하하거나 회전 중인 물체가 키프레임 직후 잠깐 멎은 뒤 다시 움직였다.
- 방장과 참가자의 카메라 높이가 다르면 같은 드롭도 서로 다른 높이에서 시작할 수 있었다.
- 키프레임 직후 큰 위치 변화가 꼬리 속도와 충돌 연출로 해석되어 가짜 연출이 생길 수 있었다.
- 기존 자동 테스트는 키프레임 적용 **후** 양쪽 좌표가 같아지는지만 확인했기 때문에, 사용자가 보는 순간이동을 정상 동작으로 통과시켰다.

## 원인

### 1. 두 브라우저의 물리는 자연스럽게 벌어진다

대전은 서버가 Rapier를 실행하지 않는다. 방장과 참가자 브라우저가 같은 물건을 각자 시뮬레이션하고, 승패와 복구 상태만 방장이 결정한다.

다음 값은 브라우저마다 완전히 같을 수 없다.

- `requestAnimationFrame` 호출 간격
- 물리 accumulator에 쌓이는 delta
- WebSocket 메시지를 적용하는 프레임
- 접촉과 끈적한 물건의 관절이 생성되는 시점
- 탭 전환이나 순간적인 프레임 저하

따라서 같은 시드와 물건으로 시작해도 2.5초 동안 위치·회전·접촉 구조가 조금씩 달라진다. 주기적인 권위 복구는 필요한 안전장치다.

### 2. 권위 복구의 불연속을 그대로 그렸다

기존 `PhysicsWorld.applyFrames()`는 참가자 물체를 방장이 보낸 `x`, `y`, `rotation`으로 즉시 이동시켰다. `MatchEngine`은 교정된 `physics.snapshots()`를 같은 프레임에 그대로 `ArenaRenderer`로 넘겼다.

사용자가 직전 프레임에 본 위치와 새 권위 위치 사이에 차이가 있으면 화면에서는 다음처럼 보였다.

```text
직전 프레임: 참가자 로컬 위치
키프레임 프레임: 방장 권위 위치로 즉시 변경
```

키프레임이 오기 전까지 참가자 로컬 결과를 계속 보여주다가 한 프레임 만에 방장 위치로 바뀌므로, 좌표가 정확히 복구될수록 오히려 순간이동이 선명해졌다.

### 3. 위치만 복원하고 운동 상태를 지웠다

기존 `place()`는 위치와 회전을 바꾼 뒤 선속도와 회전 속도를 모두 0으로 만들었다. 이 때문에 낙하·회전 중인 물체도 키프레임 순간에 인위적으로 멎었고, 다음 물리 스텝부터 중력과 충돌에 의해 다시 움직였다.

또한 키프레임에는 다음 스텝과 사건 판정에 영향을 주는 상태가 없었다.

- 선속도와 회전 속도
- Rapier 휴면 상태
- 정착·앵커·이탈 상태
- 정착 타이머와 기준 위치
- 직전 속도 및 충격 파생 상태

좌표만 맞아도 내부 상태가 다르면 다음 스텝부터 다시 다른 결과가 나올 수 있었다.

### 4. 드롭 시작 높이가 로컬 카메라에 의존했다

기존 `dropped` 메시지는 조준 위치와 물건 ID만 보냈다. 양쪽은 각자의 `cameraY`로 생성 높이를 다시 계산했다. 이미 카메라가 조금이라도 다르면 같은 물건이 처음부터 서로 다른 높이에서 떨어져 발산이 시작됐다.

## 원인을 찾은 과정

### 1. 메시지에서 렌더링까지 경로를 추적했다

다음 순서로 코드를 따라갔다.

```text
MatchEngine의 2.5초 sync 전송
  → 참가자의 sync 수신
  → PhysicsWorld.applyFrames()
  → place()의 즉시 위치 변경과 속도 초기화
  → 같은 프레임의 ArenaRenderer.draw()
```

이 경로에서 물리는 정상적으로 방장 좌표에 수렴했지만, 수렴 과정이 화면에 그대로 노출된다는 것을 확인했다.

### 2. 기존 테스트의 사각지대를 확인했다

기존 물리 동기화 테스트는 `applyFrames()` 호출 뒤 참가자 좌표가 방장과 같아지는지만 검사했다. 깜빡임은 **적용 직전 표시 위치와 적용 직후 표시 위치의 차이**인데, 그 차이를 관찰하는 테스트는 없었다.

이에 방장과 참가자 물리 세계를 일부러 다른 위치로 만든 뒤 다음을 나눠 검사했다.

1. 참가자 실제 물리가 즉시 방장 값으로 복구되는가
2. 키프레임 직후 첫 표시 위치는 직전 화면과 이어지는가
3. 정해진 시간이 지나면 표시 위치도 권위 위치와 같아지는가

### 3. 위치 외의 상태를 하나씩 비교했다

좌표를 맞춘 직후에도 다시 발산할 수 있는 값을 추적했다. 그 결과 속도뿐 아니라 휴면·정착·앵커·이탈과 충격 파생 상태가 다음 물리 스텝과 연출에 영향을 주는 것을 확인했다.

끈적한 물건의 관절도 별도로 확인했다. 같은 `itemId` 쌍이라도 접촉 당시 로컬 앵커와 상대 회전이 다를 수 있으므로, 관절 목록이 같다는 이유만으로 참가자 관절을 유지하는 최적화는 안전하지 않았다.

### 4. Chrome 루프백에서 실제 렌더링을 확인했다

개발용 Chrome 루프백 대전에서 참가자 물체를 약 0.35m 일부러 어긋나게 한 뒤 다음 키프레임을 받게 했다.

- 기록된 교정 거리: `0.349994m`
- 250ms 뒤 방장·참가자 물리 위치 차이: `0.0000074m`
- 렌더링된 캔버스: 2개 모두 정상
- 브라우저 예외: 없음

이 확인으로 교정량이 표시 보정에 전달되고, 보정 종료 후 실제 권위 물리와 다시 합쳐지는 것을 검증했다.

## 해결 방법

### 1. 물리는 즉시 복구하고 화면만 부드럽게 보정했다

`src/multi/BodyCorrection.ts`에 참가자 전용 표시 보정 계층을 추가했다.

`PhysicsWorld.applyFrames()`는 교정 전 위치와 권위 위치의 차이를 반환한다. 참가자 물리는 즉시 권위 상태가 되지만, `MatchEngine`은 렌더링할 스냅샷에만 반대 방향 오프셋을 더한다.

```text
표시 위치 = 권위 물리 위치 + (교정 전 위치 - 권위 위치) × 남은 비율
```

남은 비율은 120ms 동안 `smoothstep`으로 1에서 0까지 줄어든다. 따라서 키프레임 직후 첫 화면은 사용자가 직전에 보던 위치와 정확히 이어지고, 120ms 뒤에는 표시 위치도 권위 위치와 같아진다.

이 처리는 `MatchEngine`에만 있다. `ArenaRenderer`는 네트워크, 방장, 참가자 개념을 모른 채 전달받은 바디를 그린다.

### 2. 큰 차이는 부드럽게 끌지 않고 즉시 반영했다

다음 기준을 넘는 교정은 붕괴나 큰 불일치로 보고 즉시 스냅한다.

- 위치 차이: `0.75m` 초과
- 회전 차이: `60°` 초과

큰 붕괴를 120ms 동안 잘못된 위치에 남겨두면 물체가 충돌 위치와 다른 곳에 보일 수 있기 때문이다. 회전은 `-π`와 `π` 경계를 넘을 때 가장 짧은 방향을 사용한다.

### 3. 교정을 새로운 충돌이나 빠른 이동으로 해석하지 않게 했다

권위 교정은 게임 안에서 실제로 일어난 충돌이 아니다. 다음 부작용을 막았다.

- 교정 직후 한 물리 스텝의 가짜 impact 억제
- 표시 보정 중인 바디의 꼬리 속도 계산 제외
- 큰 차이로 즉시 스냅한 바디도 한 렌더 동안 꼬리 계산 제외

이를 통해 위치 복구가 착지음, 충돌 효과, 긴 부스러기 꼬리로 중복 표현되지 않게 했다.

### 4. 권위 프레임이 다음 물리 스텝에 필요한 상태를 복원하게 했다

`AuthorityBodyFrame`의 현재 형식(`stateVersion: 1`)에 다음 값을 포함했다.

- `vx`, `vy`, `angularVelocity`
- `sleeping`, `settled`, `anchored`, `lost`
- `settleTimer`, `restX`, `restY`, `previousSpeed`
- `dislodged`, `impacted`, `struck`

참가자는 이 값을 Rapier 바디와 게임 파생 상태에 함께 적용한다. 구형 위치 전용 프레임도 허용하지만, 새 상태가 없다는 이유로 참가자의 기존 정착·앵커·휴면 상태를 지우지는 않는다.

관절은 권위 위치를 적용한 뒤 방장 목록으로 전체 재구성한다. 같은 물건 쌍이라도 접촉 앵커가 다를 수 있어 단순 목록 비교 최적화는 적용하지 않았다.

### 5. 모든 드롭이 같은 높이에서 시작하게 했다

방장이 계산한 `spawnY`를 `dropped` 메시지에 포함했다. 참가자는 자기 카메라로 다시 계산하지 않고 방장 값을 그대로 사용한다. 구형 메시지에 `spawnY`가 없을 때만 기존 계산을 호환 경로로 사용한다.

### 6. 잘못된 권위 메시지가 상태를 파괴하지 않게 했다

키프레임 적용 경로를 함께 강화했다.

- 방장이 아닌 발신자의 권위 메시지 거부
- 다른 `matchId`의 메시지 거부
- 중복 `itemId`가 있으면 `sync` 전체 거부
- 존재하지 않는 물건이나 자기 자신을 가리키는 관절 거부
- 유효하지 않은 숫자, 범위 밖 속도, 불완전한 현재 프레임 거부
- 다음 판 엔진을 만드는 중 도착한 판 ID 없는 구형 `drop`·`rematch` 재생 방지

중계 서버는 방장 ID를 소켓 순서로 다시 추측하지 않고 Durable Object 저장소와 WebSocket attachment에 보존한다. 참가자는 이 ID와 일치하는 발신자의 권위 메시지만 적용한다.

## 결과

### 자동 검증

최신 `main`과 통합한 최종 상태에서 다음 검증을 통과했다.

- `pnpm test`: 70개 파일, 658개 테스트 통과
- `pnpm typecheck`: 통과
- `pnpm build`: 통과
- `pnpm dlx wrangler deploy --dry-run --config worker/wrangler.toml`: 통과
- `pnpm lint`: 오류 없음. 기존 React hooks 의존성 경고 2개만 남음

추가된 회귀 테스트는 다음을 확인한다.

- 첫 표시 프레임이 교정 전 위치와 이어지고 120ms 뒤 권위 위치가 되는가
- 회전이 `±π` 경계에서 짧은 방향으로 보정되는가
- 큰 교정이 즉시 반영되고 꼬리 연출이 억제되는가
- 권위 프레임이 속도와 파생 상태를 복원하는가
- 구형 위치 프레임이 기존 파생 상태를 파괴하지 않는가
- 잘못된 바디·중복 ID·유효하지 않은 관절이 있는 `sync`를 통째로 거부하는가
- 방장 외 발신자와 다른 판의 권위 메시지를 무시하는가
- 방장이 계산한 `spawnY`를 양쪽이 똑같이 사용하는가

### 브라우저 확인

Chrome 루프백에서는 0.35m의 의도적인 오차가 다음 키프레임 뒤 권위 위치로 수렴했고, 캔버스 두 개 모두 예외 없이 렌더링됐다. 물리 판정은 키프레임 수신 즉시 방장 상태가 되었고 표시 오프셋만 짧게 남았다.

### 비용과 구조

- 키프레임 주기는 기존 2.5초를 유지했다.
- 10Hz 상시 상태 스트리밍을 추가하지 않았다.
- 서버에서 Rapier를 실행하지 않는다.
- 싱글 물리와 `ArenaRenderer`에는 네트워크 책임을 넣지 않았다.

## 남은 확인

아직 실제 Cloudflare 중계와 서로 다른 두 기기 조합에서는 확인하지 않았다. 다음 항목은 배포 전 실기 검증이 필요하다.

- 실제 네트워크 지연에서 120ms 보정이 자연스러운가
- 특정 물건이나 큰 탑에서 0.75m 이상의 교정이 반복되는가
- 탭 전환과 프레임 저하 뒤에도 빠르게 수렴하는가
- 표시 위치와 착지음·부스러기 위치가 눈에 띄게 어긋나지 않는가

큰 교정이 반복될 때만 드롭 사건을 동일한 고정 물리 틱에 적용하는 후속 설계를 검토한다. 현재 단계에서는 2.5초 키프레임과 짧은 표시 보정으로 비용을 늘리지 않고 증상을 해결하는 쪽을 선택했다.
